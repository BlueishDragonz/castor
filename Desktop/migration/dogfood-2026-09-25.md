# Dogfood walkthrough — 2026-09-25

**Branch**: `release/astro-migration` (HEAD `963efa7`)
**Tester**: Hermes (via Camofox browser + JS inspection + backend grep)
**Build**: dev stack on homelab2 (`scripts/dev-up.sh`), demo seed active

test-suite status, not a real walkthrough. Retracted.

## UI/UX inconsistencies (the visible ones)

### 1. Back-link placement is inconsistent across the app

| Page | Back affordance | Where |
|---|---|---|
| `/habits` | none | — |
| `/circles` | `← Back to habits` text link | **top-right**, stacked above the "New circle" CTA |
| `/circles/new` | back-arrow icon | top-left of title row ✅ (the pattern user wants) |
| `/circles/[id]` | back-arrow icon + crown icon + title | top-left, single row ✅ |
| `/habits/new` | `← Back to habits` text link | **right of title**, floating |
| `/stats` | `← Back to habits` text link | right of title |
| `/settings` | `← Back to habits` text link | right of title |
| `/security` | (couldn't load — likely similar) | unknown |
| `/tokens` | `← Back to habits` text link | below title, full-width row |
| `/account/delete` | `← Back to habits` text link | right of title |
| `/help` | none | — |
| `/terms`, `/privacy` | `← Back to home` text link | bottom of article, separate from header |
| `/habits/[id]` | none | — |

Two patterns exist:
- **Pattern A (icon-left-of-title)**: `/circles/new`, `/circles/[id]` — what the
  user wants.
- **Pattern B (text-link-right-of-title)**: every other page that has a back
  link.

Plus several pages have no back link at all (`/habits`, `/habits/[id]`, `/help`),
even though a user landing on them from a deep link has no way out.

### 2. Desktop menu is a floating ghost-button with no chrome

`DesktopMenu.tsx` renders as a `hidden lg:block fixed top-4 right-4 z-50`
ghost Button (no border, no background until hover). At desktop width it
sits alone in the top-right corner — no header bar, no surrounding
container. Looks like a stray icon.

The mobile equivalent (`BottomNav`) hides correctly at ≥641px, so what
the user sees on desktop is just this one floating hamburger. Multiple
reviewers would call this "looks unfinished".

### 3. /habits home page has visible composition issues

- Day-of-week headers (`MON 25 / TUE 24 / ...`) **float disconnected**
  above the habit rows with a visible gap and no visual band.
- `+ Add habit` is a plain text link with no button styling — doesn't
  read as actionable.
- Layout is **centered in a narrow column** with massive white space on
  both sides — feels under-utilised on desktop viewports.
- Habit rows use `h-3` headings and tiny tag pills that compete with
  each other visually.

### 4. Inner form pages have inconsistent button placement

- `/circles/new`: "Cancel" (text) and "Create circle" (green button)
  run together with no gap.
- `/habits/new`: same problem — "Cancel" (text) and "Create" (green)
  are adjacent, the Cancel text almost touches the button edge.
- `/circles/[id]` Invites card: Delivery / Email / Expires hours /
  Mint invite are jammed into one horizontal row — the Expires
  spinbox is rendered at ~30px wide and is hard to use.

These should be **stacked vertically** (label above input) and the
primary action should sit on its own line with clear separation.

### 5. The "Delete circle" button is visually too prominent

At `/circles/[id]` the destructive button sits **below all cards as a
standalone red button** with a trash icon. On every other page
destructive actions are de-emphasised (e.g. `/settings` has a small
red link). The circle page makes it look like the primary action.

### 6. Section headings inside cards are oversized

`/circles/[id]` uses `<h3>` for "Members (1)", "Shared habits (0)",
"Recent activity (last 14 days)", "Invites" — these render at near-`h2`
size and visually dominate the empty cards below them (e.g. the
"Recent activity" card is mostly empty space + one line of text).

### 7. a11y: aria-label leaks into heading text

The accessibility tree on `/circles/[id]` reads the page title as:

> "You own this circle Family wellness"

because the crown icon (decorative but `aria-label="You own this
circle"`) sits inside the `<h1>`. Screen readers will hear the owner
status as part of the heading, then the title. Not catastrophic, but
wrong.

`h1` text is actually "Family wellness" (the a11y tree and the visible
text don't match).

### 8. /habits/[id] heatmap column alignment is broken

The 3-month heatmap on the habit detail page packs all days across a
single grid that doesn't respect weekly columns. Days from different
weeks appear interleaved in the same row. Users cannot tell which day
is which weekday without checking the date number tooltip.

### 9. /habits/[id] form defaults to a future date

The "Mark a date" date picker defaults to `2026-09-25` regardless of
the current date. If the test runs in the morning the user may pick
today; if they don't change it, they may submit a date that's wrong
(some heatmaps showed green ticks for dates that don't yet exist on
the grid).

### 10. `pages/api/v1/user-configs` PUT documents itself as writing
to the server but UI says "Per-device" and "applies on next visit".

`/settings` Display card calls these "Per-device" and says "applies on
next visit" — but the slice-12 backend test confirmed they are written
to `user_configs` and survive device changes. Either the copy is
misleading or the behaviour changed. Worth verifying in slice 22.

### 11. Bottom-nav leak on /security

`/security` stayed at "Loading..." for the entire walkthrough, even
though `astro check` is clean. Could be a JS hydration error or an
auth state race. Needs a separate investigation.

## Circles feature gaps (substantive)

The current Circles implementation is functional but minimal. The user
asked for a "rich" flow. Concrete gaps:

### A. No email delivery — invite is link-only

`castor/app/circle_routes.py` creates an invite with `token_hash` but
**never calls `send_email`**. The "Delivery: Email" option in the
dropdown just changes the invite record's `invited_email` field; the
inviter still has to copy the token URL manually.

User wanted: "send an invite (beautiful HTML templated invitation
email)". Currently impossible.

### B. Invite token is hidden from the inviter

When the inviter clicks "Mint invite", the token is returned in
`?new_token=...` URL param but **never rendered as a copyable link or
displayed as text**. The success state shows only
"link expires 28/09/2026, 14:17:46" with no way to actually share it.
Bug.

### C. No guard against self-join (real backend bug)

Walked through: minted invite as demo, accepted as demo with my own
token → 201 Created, demo is now both owner AND member of the same
circle. `accept_invite` in `circle_routes.py:480-512` checks the token
but never checks `invite.invited_by != user.id`. Confirmed in the
SQLite dev DB:

```
sqlite> SELECT * FROM circle_member;
1|1|aac2d416-1b0d-4fc6-b558-9c96a10192b9|...
```

Owner appears as a member row. Bug.

### D. Join page only redirects to /login, never /register

`/circles/[id]/join.astro:8`: `if (!Astro.locals.session) return
Astro.redirect('/login');`. User wanted: "redirected to signup if new
or login if existing". Currently an unauthenticated user with no
account just hits `/login` and fails. No path to /register from a
circle invite.

### E. Join error UX is opaque

On missing token: redirects to `/circles/{id}?err=join_no_token`. No
visible error message on the destination page — the user just lands
on the circle detail (which they probably can't see anyway because
they're not a member).

### F. No "share your habits with this circle" wizard

After accepting, user lands on `/circles/{id}` showing the owner's
existing shared habits. There is no flow that asks the new member:
"would you like to share any of your habits with the people in this
circle?" → habit picker → visibility selector. The user's spec
explicitly mentioned this.

### G. No join confirmation summary

After accepting, no page tells the member what they can now see (the
owner's shared habits) vs. what they shared (if they did pick habits).
User spec wanted: "confirm they've joined the circle with a summary
of what they can see (what is shared with them) and what they shared
with the inviter (if they selected any habits)".

### H. Invitee email field doesn't send an invite-email

Even if the inviter types the invitee's email, no email goes out.
The email field is stored but unused for delivery. The user said
"send an invite (beautiful HTML templated invitation email)" — that's
a full HTML email template + SMTP/transactional-email integration.
Currently zero.

### I. Crown icon a11y leakage (already noted in #7)

### J. Owner-only Member management has no UI for member self-removal
   that we walked through.

`/circles/[id]/leave.astro` and `/members/[user_id]/remove.astro`
exist as routes — but the circles/[id] page didn't surface a
"Remove member" button per member row (only the owner was listed
because the only member was demo).

## What this means for cutover

PROGRESS.md was written under the assumption that:

> "Frontend has 35 Astro pages, 17 BFF endpoints, 18 shadcn primitives"

— which is correct from a file-inventory perspective but completely
silent on the user experience of moving through them. The cutover
runbook (slice 19) assumes the UI is shippable; it is not.

**Recommendation**: do **not** cut over yet. Plan at least two more
slices before the deploy:

- **Slice 22 — UI consistency pass** (Header / back link / button
  alignment / heatmap column alignment / section heading size). This
  is mechanical but touches ~15 pages.
- **Slice 23 — Rich Circles** (email delivery + HTML template +
  self-join guard + join wizard + summary page + error UX). Larger
  scope; might split into 23a (backend + tests) and 23b (UI).

Cutover should happen after both slices, against a clean demo seed.
